## Executive verdict

The V2 architecture is the correct response to the Dollers V1 board failure, but the current repository is an early prototype rather than a safe massively parallel coordinator.

The design gets the major boundaries right: one structured file per task, a generated human-readable board, JSON Schema validation, an explicit audit SHA, repository-level claim exclusion, separate peer and human review states, and evidence-bearing handoffs. Those choices directly address the monolithic-board, duplicate-ID, stale-audit, and review-bottleneck problems found in V1.

The implementation does not yet enforce most of those promises. The CLI has only `lint`, `render`, and `claim`; it is not in a Git repository; claims are neither locked nor atomic; the generated board remains a shared merge-conflict surface; lifecycle transitions, dependencies, audit freshness, lane eligibility, evidence capture, peer review, archive movement, and handoff validation are not implemented. The schema validates shape weakly but not state-dependent invariants.

My recommendation is to keep the architecture, correct the README's maturity claims, and harden the coordinator in a narrow sequence: repository/bootstrap safety, schema invariants, atomic local transactions, complete lifecycle commands, executable verification, structured review artifacts, and only then distributed coordination.

## Strengths worth preserving

### 1. Per-task records are the right decomposition

Moving active tasks from one 190 KB Markdown file into isolated YAML records dramatically improves context targeting, reviewability, and conflict isolation. It also makes schema enforcement possible.

This should remain the foundation.

### 2. Generated Markdown is a good human interface

Humans should not have to read raw YAML to understand fleet state. A generated `TASKS.md` is a good compatibility and visibility layer.

The important correction is that generated output should not itself become authoritative shared state or a required participant in every concurrent claim commit.

### 3. `audited_repo_sha` is directionally correct

Pinning an audit to repository state is substantially better than a timeless `AUDITED` label. It creates the possibility of detecting task drift mechanically.

The current implementation does not perform that check, but the field is still the right starting point.

### 4. The lifecycle separates peer and human review

`PEER_REVIEW` and `HUMAN_REVIEW` represent different kinds of confidence and authority. This is an important improvement over one overloaded REVIEW state.

Peer review should remove technical defects and verify evidence. Human review should be reserved for visual judgment, editorial authority, legal approval, strategic decisions, and irreversible actions.

### 5. The handoff schema captures useful provenance

Agent, model, target repository, branch, base SHA, head SHA, and evidence output are appropriate required fields. These would make agent output traceable if the schema were connected to an actual command and validation path.

### 6. Repository-level exclusion is a sensible initial lock granularity

One active worker per spoke repository is conservative, but appropriate for repositories using shared worktrees and generated artifacts. Path-level concurrency can come later.

## Critical gaps

### 1. This is not currently a Git repository

Running Git status in `task_coordinator` returns:

```text
fatal: not a git repository (or any of the parent directories): .git
```

The README instructs agents to commit claims immediately, but that is impossible. There is no durable history, blame, rollback, remote visibility, or compare-and-swap behavior.

Until Git or another shared transaction service exists, the coordinator is a collection of local files, not a fleet-wide coordination system.

**Required correction:** initialize version control, define the authoritative remote/private visibility model, and document whether claim commits are automatically pushed. A local commit alone cannot coordinate agents on separate machines.

### 2. “Database-backed” is inaccurate

The authoritative store is a directory of YAML files. That is a valid structured file store, but it is not a database in the normal transactional sense.

This matters because the README then claims support for “massively parallel agent swarms without Git merge conflicts.” The current store provides no transactions, locks, uniqueness constraints, compare-and-swap updates, or durable indices.

**Recommended wording now:** “schema-validated, file-backed task store.” Reserve “database-backed” for a transactional implementation.

### 3. The generated board recreates a shared merge-conflict surface

Per-task YAML files reduce conflicts only if agents modifying separate tasks do not also modify the same generated file. `cmd_claim` always calls `cmd_render`, which rewrites `TASKS.md`.

Therefore two agents claiming different tasks on different branches or clones still both modify `TASKS.md`. Their task YAML files may merge cleanly, but the generated board can conflict.

**Required correction:** do not require agents to commit generated `TASKS.md` with claims. Generate it after accepted state changes through a serialized coordinator, CI job, pre-commit hook, or human-side refresh. Generated artifacts should be reproducible, not concurrency-critical.

### 4. Claims have a classic time-of-check/time-of-use race

`cmd_claim` performs:

1. read every task;
2. find the requested task;
3. inspect repository locks;
4. mutate memory;
5. overwrite the task YAML;
6. overwrite `TASKS.md`.

There is no filesystem lock, remote transaction, expected-version field, or atomic compare-and-swap. Two processes can both read an unlocked state and both succeed.

Writing the task file and board is also a two-file partial transaction. If rendering fails after the YAML write, canonical state and human view disagree.

**Local-mode correction:** hold an exclusive lock around load/check/write/render; write temporary files, `fsync`, and atomically replace targets; include a monotonically increasing task revision.

**Distributed-mode correction:** serialize claims through a service/bot or remote merge gate. Git pushes alone detect file conflicts after the fact but do not reliably enforce repository locks across different task files.

### 5. Lifecycle transitions are not implemented

The README presents a strict lifecycle, but the CLI implements only the AUDITED-to-CLAIMED transition. Everything else requires manual YAML edits.

An agent can manually change `OPEN` directly to `DONE`, omit evidence, bypass peer review, or alter ownership. The schema will accept it.

At minimum, implement:

```text
fleet create
fleet audit
fleet claim
fleet start
fleet block
fleet unblock
fleet verify
fleet submit-review
fleet record-review
fleet request-human-review
fleet close
fleet defer
fleet cancel
fleet archive
```

Each command should define allowed prior states, required fields, actor role, timestamps, and emitted artifacts.

### 6. The schema lacks conditional invariants

The task schema requires only:

- `id`;
- `title`;
- `repo`;
- `priority`;
- `lane`;
- `status`;
- `created_at`;
- `scope`;
- `definition_of_done`.

Consequently:

- AUDITED can omit all audit metadata;
- CLAIMED can have a null owner;
- OPEN can have a stale owner;
- DONE can omit verification and handoff references;
- BLOCKED can omit a reason;
- HUMAN_REVIEW can omit the requested human action;
- task dependencies can reference nonexistent IDs;
- audit SHA can be any string;
- filenames can disagree with task IDs.

Use JSON Schema `allOf` with `if`/`then` conditions for status-dependent requirements, plus application-level cross-record validation for uniqueness and dependency existence.

### 7. Date-time validation is not actually active

The schema declares `format: date-time`, but `jsonschema.validate()` does not enforce formats without a `FormatChecker`.

This was confirmed empirically: `created_at: not-a-date` passed.

Use the validator appropriate to the declared draft and pass `format_checker=jsonschema.FormatChecker()`.

### 8. Unknown fields are accepted

The task and handoff schemas omit `additionalProperties: false`. A misspelled field can silently pass, creating a false sense that the value is enforced.

For example, `verification_comand` would be accepted while the actual `verification_command` remained absent.

Set `additionalProperties: false` at every controlled object boundary.

### 9. Duplicate task IDs are not detected

One purpose of V2 is preventing V1's duplicate-ID failures, but `load_all_tasks()` loads a list without checking uniqueness. `cmd_claim` claims the first matching ID returned by filesystem iteration, which is not a stable ordering contract.

The task ID pattern alone does not ensure unique values across files.

`fleet lint` must verify:

- unique task IDs;
- filename equals `<id>.yaml`;
- dependency IDs exist;
- no cycles where disallowed;
- no multiple active repository locks.

### 10. The sole migrated task proves audit drift is not enforced

`T-MIN-001` is AUDITED against `b51d4e4`. The current Minchiate `test` HEAD is:

```text
e86333a37de43f863847c0f68d1514413beaa9b1
```

The intervening `db7d274` commit already contains `minchiate_reviewer.py`, `tools/reviewer_app/`, and the existing ledger/grid work that the task says to create.

The task's verification command is:

```text
python3 minchiate_reviewer.py --check
```

The current script contains no argument parser and no `--check` handling; it unconditionally starts Flask in debug mode when executed. The proposed verification command is therefore not a valid bounded verification command.

This shows that storing an audit SHA is insufficient. Claim must compare it with current target state and require re-audit or an explicit compatibility decision. Audit must also test the verification command at authoring time.

### 11. A Git SHA alone does not describe a dirty worktree

The V1 dispatch incident showed a second issue: a repository can have the same HEAD while important tracked or untracked working files change beneath it.

An audit should record whether the worktree was clean. Claims should refuse or explicitly surface overlapping dirty paths.

Potential fields:

```yaml
audited_repo_sha: e86333a...
audited_worktree_clean: true
audited_at: 2026-08-10T16:00:00-06:00
audit_expires_at: 2026-08-17T16:00:00-06:00
owned_paths:
  - minchiate_reviewer.py
  - tools/reviewer_app/
```

### 12. Dependencies are stored but never enforced

`dependencies` appears in the schema and sample, but `cmd_claim` does not inspect it. A task can be claimed while a dependency is OPEN, BLOCKED, or absent.

Dependencies need a defined satisfaction policy, normally DONE or a task-specific accepted state.

### 13. Lane eligibility is not enforced

The task stores `lane`, but `claim` accepts any owner string and does not receive or validate a platform identity. A Codex worker can claim a HUMAN-only task; a generic owner can claim a codex-specific task.

Separate human-readable owner identity from platform/lane identity and validate both.

### 14. Repository identity is only a free-form string

The CLI cannot verify audit SHAs, branch state, dirty worktrees, or remote freshness because it has no repository registry mapping `minchiate_tarot` to a path and branch policy.

Add a controlled repository registry, for example:

```yaml
repos:
  minchiate_tarot:
    path: ../minchiate_tarot
    branch_policy: test
    remote: origin
```

Validate that paths resolve inside approved workspace roots.

### 15. Claim leases and stale ownership do not exist

The schema lacks `claimed_at`, heartbeat, lease expiry, session ID, or release mechanism. An abandoned claim can lock a repository forever.

Recommended fields:

```yaml
claim:
  owner: codex
  model: GPT-5
  session_id: ...
  claimed_at: ...
  lease_expires_at: ...
  last_heartbeat_at: ...
```

Do not automatically steal expired work without checking the target worktree, but surface stale leases clearly.

## Handoff and verification gaps

### 16. The handoff schema is disconnected

There is a handoff schema and an empty `handoffs/` directory, but no command loads, creates, or validates handoffs. `fleet lint` checks tasks only.

Tasks past PEER_REVIEW should require a handoff reference whose document validates and whose task ID and SHAs match the task.

### 17. Evidence validation is nominal

`evidence_output` requires only a string of ten characters. That does not prove:

- which command ran;
- when it ran;
- exit status;
- which commit was tested;
- whether output was truncated;
- whether secrets were redacted;
- whether the command timed out.

Evidence should be captured by `fleet verify`, not pasted by the worker.

Suggested structure:

```yaml
verification_runs:
  - command_argv:
      - python3
      - minchiate_reviewer.py
      - --check
    cwd: /approved/repo/path
    started_at: ...
    finished_at: ...
    exit_code: 0
    stdout_tail: ...
    stderr_tail: ...
    tested_sha: ...
    timed_out: false
```

Prefer an argument array over an unrestricted shell string. Add timeouts, output limits, environment allowlisting, and redaction.

### 18. PEER_REVIEW has no review artifact or verdict model

The lifecycle names peer review but provides no reviewer dispatch, schema, severity classification, or transition gate.

Add `schemas/review.schema.json` with:

- reviewer agent/model;
- reviewed base/head SHA;
- requirements reviewed;
- findings with severity and file/line evidence;
- verdict: PASS, PASS_WITH_CORRECTIONS, or FAIL;
- correction resolution records;
- review timestamp.

HUMAN_REVIEW should be unreachable while unresolved Important/Critical findings exist.

### 19. Human review requirements are not used

`human_review_required` exists but does not affect transitions or rendering beyond being invisible. A task marked false should be able to close after passing peer review; a task marked true should require a concrete human-review request.

### 20. Archive behavior is absent

The directory exists, but no command moves DONE/CANCELLED tasks to archive. Without archive mechanics, the generated board will eventually reproduce V1's completed-task bloat.

Archive should preserve task record, handoff, review artifacts, and final SHAs together or through stable references.

## Operational and packaging gaps

### 21. There are no automated tests

No test suite is present for the task coordinator itself. This is particularly risky because concurrency and transition correctness are the core product.

Minimum test categories:

- schema acceptance/rejection;
- every legal and illegal transition;
- duplicate IDs and filename mismatch;
- dependency checks;
- repository-lock conflict;
- two-process claim race;
- interruption during save/render;
- stale audit and dirty worktree;
- stale claim lease;
- handoff/review cross-reference validation;
- deterministic render output;
- archive behavior;
- command timeout and evidence redaction.

### 22. Dependency installation is not reproducible

The repository contains a `.venv`, but no `requirements.txt`, `pyproject.toml`, or setup metadata. The wrapper assumes that exact local virtual environment exists.

This will fail on another machine or after the directory moves.

Add a minimal `pyproject.toml`, lock dependencies, and have the wrapper fail with an actionable setup message rather than sourcing a missing environment.

### 23. `.gitignore` is absent

There is no `.gitignore`, despite the in-repository virtual environment and future evidence artifacts. Before initializing Git, add exclusions for `.venv`, caches, local locks, temporary files, captured raw secrets, and any non-versioned evidence.

### 24. YAML loading failures are not handled cleanly

Malformed YAML, empty documents, permission errors, or non-object documents can crash commands rather than produce per-file lint errors. The linter should identify the exact file and continue reporting all failures.

### 25. Writes are not atomic

`save_task` and `cmd_render` write directly to destination files. Process interruption can truncate either one.

Use a temporary file in the same directory, flush and `fsync`, then `os.replace`. Preserve permissions where relevant.

### 26. Rendering is not validated first

`fleet render` loads tasks and indexes required fields without schema validation. A malformed task can crash rendering after partially truncating `TASKS.md`.

Render should validate all records and cross-record invariants before opening the output file.

### 27. Sorting is not a dispatch algorithm

Render sorts by repository, priority, and alphabetical status. It does not provide a deterministic “next task” query based on lane, dependency readiness, audit freshness, deadline, or existing locks.

Add `fleet next --lane codex --repo minchiate_tarot` and make it the authoritative dispatch selection logic.

### 28. Status presentation hides important differences

OPEN, AUDITED, BLOCKED, DEFERRED, and CANCELLED all receive the generic clipboard icon. CLAIMED and IN_PROGRESS share one icon. This is harmless for a one-task board but insufficient at fleet scale.

The generated board should show active claims, blocked reasons, stale audits, aging reviews, and human actions as distinct sections.

### 29. Manual task creation bypasses the CLI

The README tells humans to create YAML files manually. That preserves the opportunity for filename mismatch, duplicate IDs, invalid timestamps, and missing conditional fields.

Provide `fleet create` and `fleet audit`; reserve direct YAML editing as an advanced escape hatch followed by strict linting.

### 30. Security boundaries for verification commands are undefined

Once `fleet verify` executes task-provided commands, task YAML becomes executable authority. That is acceptable only if audit authors are trusted and commands are constrained.

Document:

- who may author or audit verification commands;
- allowed working directories;
- whether shell expansion is permitted;
- timeout limits;
- environment-variable handling;
- secret redaction;
- network policy;
- destructive-command rejection.

## README corrections needed now

Before implementation catches up, the README should avoid claiming:

- a database-backed architecture;
- massive parallel safety;
- elimination of Git merge conflicts;
- automatic repository locking as a concurrency guarantee;
- mechanically enforced handoffs;
- automated peer review.

Accurate current description:

> V2 is a schema-validated, file-backed prototype. It supports rendering and basic single-process claims. Lifecycle enforcement, atomic concurrency, Git-backed shared state, evidence capture, and review automation are under development.

That framing is not a criticism of the direction; it prevents agents from placing production trust in controls that do not exist yet.

## Recommended implementation order

### Phase 0 — Make the prototype reproducible

1. Add `.gitignore` before initializing Git.
2. Add `pyproject.toml` and locked dependencies.
3. Initialize Git and define the private remote/claim-push policy.
4. Add a test framework and CI command.
5. Correct README maturity language.

### Phase 1 — Make lint meaningful

1. Add `additionalProperties: false`.
2. Enable `FormatChecker`.
3. Add status-dependent schema conditions.
4. Validate unique IDs and filename/ID agreement.
5. Validate dependencies and repository names.
6. Handle malformed files without crashing.
7. Lint handoffs and review artifacts.

### Phase 2 — Make local state transitions safe

1. Add a global coordinator lock.
2. Add atomic task and board writes.
3. Add task revision numbers.
4. Implement the full transition command set.
5. Add claim timestamps, leases, and release behavior.
6. Add comprehensive transition and race tests.

### Phase 3 — Make audit and verification real

1. Add repository registry/path resolution.
2. Check audited SHA, branch, remote relationship, and dirty worktree.
3. Require verification commands during audit.
4. Implement bounded `fleet verify` evidence capture.
5. Bind evidence to tested commit SHA.

### Phase 4 — Make review enforceable

1. Add a structured review schema.
2. Require review artifacts for review transitions.
3. Block promotion on unresolved serious findings.
4. Route human-review-required tasks explicitly.
5. Add review age and ownership to generated views.

### Phase 5 — Support distributed concurrency honestly

Choose one model explicitly:

#### Shared-filesystem coordinator

All agents operate against one checkout. Use filesystem locks and atomic writes. Simpler, but not cross-machine.

#### Central coordinator service

Expose authenticated task transitions through a small API backed by SQLite/PostgreSQL with transactions and uniqueness constraints. Best fit for true multi-machine swarms.

#### Serialized Git coordinator bot

Agents submit claim requests; one bot validates repository locks and commits canonical state. Keeps Git as ledger but centralizes transitions.

Do not describe ordinary independent Git clones editing YAML as atomic distributed locking. They are not.

## Acceptance criteria for calling V2 production-ready

V2 should not be called production-ready until all of the following are demonstrated by automated tests:

1. Duplicate IDs cannot pass lint.
2. An AUDITED task without valid audit metadata cannot pass lint.
3. A stale audit cannot be claimed silently.
4. A task with unmet dependencies cannot be claimed.
5. A worker in the wrong lane cannot claim a restricted task.
6. Two concurrent claims for the same repository cannot both succeed.
7. Interrupted writes cannot corrupt task files or the board.
8. Manual illegal transitions are detected.
9. Verification evidence is captured with exit code and tested SHA.
10. A task cannot enter HUMAN_REVIEW without a valid peer-review artifact.
11. A task cannot enter DONE without required evidence and approvals.
12. Completed tasks archive without remaining on the active board.
13. Fresh installation works without a prebuilt `.venv`.
14. Generated views are deterministic and do not create claim-time merge conflicts.
15. Distributed visibility and claim arbitration have a documented, tested authority.

## Final recommendation

Continue with V2. The architecture is substantially better than V1 and is worth hardening.

However, treat the current codebase as a specification spike. Its present green lint result and repository-lock message are not sufficient evidence of task integrity or concurrency safety. The immediate milestone should be a single-process, fully tested coordinator that cannot perform illegal transitions and writes atomically. Only after that foundation is proven should the project claim multi-agent or distributed swarm safety.

The most important cultural rule is simple: every guarantee stated in the README should correspond to a test that demonstrates the forbidden failure cannot occur. That is how V2 becomes an operating system rather than another set of instructions agents can accidentally bypass.
