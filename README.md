# Dollers Fleet Task Coordinator (V2)

Welcome to the **Task Coordinator (V2)** for the Dollers AI Agent Fleet. This repository acts as the central Hub for dispatching, tracking, and verifying work across all Spoke repositories (like `artmetrics.co`, `minchiate_tarot`, etc.).

This system replaces the monolithic `TASKS.md` flat-file with a database-backed, schema-enforced architecture that supports massively parallel agent swarms without Git merge conflicts.

---

## 🏗️ Architecture

- **`tasks/active/`**: The database. Every active task is an isolated `.yaml` file.
- **`tasks/archive/`**: Storage for completed or cancelled tasks.
- **`schemas/`**: JSON Schema definitions that mechanically enforce what a task or handoff is allowed to contain.
- **`bin/fleet`**: The Python-based command-line interface. Agents and humans must use this to interact with the database.
- **`TASKS.md`**: A **READ-ONLY** markdown file dynamically generated by the CLI for human convenience. Never edit this file directly.

---

## 🚦 The Task Lifecycle

Tasks must follow a strict linear progression:

1. **`OPEN`**: The task is an idea. Agents CANNOT claim it.
2. **`AUDITED`**: A PM has verified the codebase, written a strict scope, and attached a `audited_repo_sha`. The task is now safe to execute.
3. **`CLAIMED`**: An agent has locked the task.
4. **`PEER_REVIEW`**: The agent is finished, has terminal evidence, and has requested an automated peer review.
5. **`HUMAN_REVIEW`**: The agent passed peer review and is awaiting final human visual/strategic sign-off.
6. **`DONE`**: The work is merged.

## 🤖 Instructions for Agents (How to Work)

If you are an agent reading this to understand how to claim work, follow these exact steps:

### 1. Find a Task
Run the render command to ensure the board is up to date:
```bash
./bin/fleet render
```
Read the generated `TASKS.md` file. Find a task that is marked **`AUDITED`** in your assigned repository lane.

### 2. Claim the Task
You must use the CLI to claim the task. The CLI will automatically check if the repository is already locked by another agent.
```bash
./bin/fleet claim T-XXX-123 --owner [YOUR_NAME]
```
If the CLI rejects your claim, you must pick a different task. If successful, it will update the YAML file and regenerate the markdown board. Commit this claim to Git immediately.

### 3. Do the Work
Navigate to the Spoke repository (e.g., `../minchiate_tarot/`) and create a `test` branch. Write the code to satisfy the `definition_of_done` found in the task's YAML file.

### 4. Provide Evidence & Complete
You are strictly bound by the "Evidence Before Claims" protocol. 
1. Run the `verification_command` listed in your task's YAML file.
2. Save the successful terminal output. 
3. Create your handoff document based on the `schemas/handoff.schema.json`.
4. Update your task's YAML file status to `PEER_REVIEW` or `HUMAN_REVIEW` and run `./bin/fleet render` to update the board.

## 👨‍💻 Instructions for Humans (How to Manage)

### Creating a New Task
Create a new file (e.g., `tasks/active/T-NEW-001.yaml`). You can use `T-MIN-001.yaml` as a template.
Ensure you fill out the `definition_of_done` and `verification_command`.

### Auditing a Task
Before an agent can work, you must change the task's status from `OPEN` to `AUDITED`. 
1. Open the task's YAML file.
2. Set `status: AUDITED`.
3. Set `audited_repo_sha` to the current Git SHA of the target repository so the agent knows exactly what codebase version the spec was written for.
4. Run `./bin/fleet lint` to ensure your YAML is valid.
5. Run `./bin/fleet render` to update the board.

### Validating the Database
If you manually edit YAML files, always run the linter to ensure you didn't break the schema:
```bash
./bin/fleet lint
```
