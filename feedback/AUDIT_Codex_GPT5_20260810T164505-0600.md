# Second Codex Audit: Task Coordinator V2 After Phases 1–3

**Agent:** Codex  
**Model:** GPT-5  
**Timestamp:** 2026-08-10 16:45:05 MDT (`20260810T164505-0600`)  
**Implementation audited:** `69e2f6f` — `Phase 3: Add 'fleet verify' to automatically capture terminal evidence`  
**Repository HEAD during final review:** `935c08b` — feedback-only change after `69e2f6f`  
**Audit method:** Static review plus adversarial execution in an isolated local clone

## Executive verdict

Task Coordinator V2 has made meaningful progress since my first review. It is now a Git repository with a configured remote, stricter schemas, format-checker invocation, duplicate-ID and filename checks, dependency-existence checks, atomic replacement for task and board files, lifecycle-oriented commands, and automatic execution of verification commands.

Those are real improvements, not cosmetic changes.

The system is still unsafe as an autonomous fleet authority because its principal gates remain bypassable. In an isolated clone, I demonstrated all of the following with exit status 0:

1. a malformed YAML file emitted an error while `fleet lint` declared that every task passed;
2. a task whose dependency was OPEN was claimed;
3. that claim proceeded while the task store contained malformed YAML;
4. a fabricated handoff containing only `head_sha: x` was accepted by `fleet submit` without running verification;
5. the human-review-required task moved from PEER_REVIEW directly to DONE;
6. the stale Minchiate AUDITED task was claimed despite the spoke having advanced and already containing the requested implementation;
7. invalid date-time data passed strict lint;
8. AUDITED tasks with null audit values passed schema validation.

The current system is best described as a rapidly improving alpha. The architecture remains sound, but the next phase should focus on making invalid state fatal and transitions evidence-bound before adding more features.

## Positive changes confirmed

### 1. Version control and remote visibility now exist

The repository has a coherent four-commit implementation history and a configured GitHub remote. This removes the most fundamental blocker from the original prototype.

The remaining policy question is whether claim commits must be pushed automatically and what authority serializes competing pushes.

### 2. Schema strictness improved

The schemas now reject undeclared fields. This protects against misspelled properties silently entering the task store.

Task status conditionals also require audit keys for audited-and-later states and require a non-empty owner for claimed-and-later states. Although the null-value gap remains, this is the correct schema direction.

### 3. Cross-record linting began

`fleet lint` now detects:

- duplicate IDs among successfully parsed files;
- filename/ID mismatch;
- dependencies referencing nonexistent successfully parsed IDs.

Those checks directly address V1 failures.

### 4. Writes are safer against simple interruption

Task records and `TASKS.md` are written to `.tmp` files and moved into place with `os.replace`. This prevents the most basic partial-destination truncation.

It does not make the overall transition atomic, but it is still an improvement.

### 5. Verification execution is now a coordinator function

`fleet verify` runs the task's verification command in the target spoke, enforces a five-minute timeout, captures exit code/stdout/stderr, refuses nonzero exits, and creates a handoff record.

This is the correct basic workflow. The remaining work is to bind the evidence to actual repository state and prevent fabricated artifacts from bypassing it.

### 6. Transition commands now exist

`audit`, `claim`, `verify`, `submit`, and `close` provide a foundation for a state machine. Even though it is incomplete, moving state mutation into named commands is preferable to direct YAML editing.

## Critical verified defects

### C-01 — Malformed task files do not fail lint

I added a scratch task file containing malformed YAML:

```yaml
id: [
```

Observed output:

```text
❌ BROKEN.yaml: Failed to parse YAML - while parsing a flow node
expected the node content, but found '<stream end>'
✅ All tasks passed strict schema validation.
lint_exit=0
```

`load_all_tasks()` prints parse errors and drops malformed records from the returned collection. `cmd_lint()` has no way to know loading failed, so it reports success.

This is more serious than an incorrect message. The omitted record is also absent from:

- duplicate-ID detection;
- dependency validation;
- repository-lock checks;
- rendering;
- task lookup.

A malformed CLAIMED task can disappear from the lock calculation, allowing another worker to claim the same repository.

**Required fix:** task loading must return records and structured load errors. Every mutating command must abort if any active task cannot be parsed and validated. Rendering must never silently omit invalid tasks.

Suggested interface:

```python
records, load_errors = load_all_tasks()
if load_errors:
    report(load_errors)
    return EXIT_INVALID_STORE
```

### C-02 — Mutations continue against a known-corrupt store

With `BROKEN.yaml` still present, `fleet claim`, `fleet submit`, and `fleet close` all printed the parse error and then returned success.

An integrity system must fail closed. Once the canonical store is known to be incomplete, no status transition is trustworthy.

**Required fix:** all commands should call one strict `load_validated_store()` preflight and refuse mutation on any parse, schema, cross-record, or lock error.

### C-03 — Dependency readiness is not enforced

Scratch fixture:

```yaml
id: T-TEST-002
status: AUDITED
dependencies:
  - T-TEST-001
```

`T-TEST-001` existed but remained OPEN.

Observed result:

```text
✅ Successfully claimed T-TEST-002 for codex.
claim_exit=0
```

Lint checks dependency existence, but claim does not check dependency state.

**Required fix:** define satisfaction explicitly. The normal rule should be all dependencies DONE. If another accepted state is allowed, encode the condition in structured dependency records.

### C-04 — Verification can be bypassed with a fabricated handoff

I created this handoff without running `fleet verify`:

```yaml
head_sha: x
```

Observed result:

```text
✅ Task T-TEST-002 submitted for PEER_REVIEW.
submit_exit=0
```

`cmd_submit()` checks only:

1. the file exists;
2. `head_sha` is not exactly `REQUIRED_PLEASE_FILL`.

It does not validate the handoff schema, task ID, agent, model, repository, branch, base SHA, head SHA format, evidence, or whether the artifact came from `fleet verify`.

**Required fix:** submit must validate the handoff schema and cross-check every identity/provenance field against the task and live repository. Prefer a coordinator-generated verification run ID or artifact hash that submit can verify.

### C-05 — Human review is bypassed by default

The scratch task contained:

```yaml
human_review_required: true
```

After the fabricated submission moved it to PEER_REVIEW:

```text
✅ Task T-TEST-002 successfully marked as DONE.
close_exit=0
```

`cmd_close()` permits both PEER_REVIEW and HUMAN_REVIEW to transition directly to DONE. It never reads `human_review_required`. There is no command that transitions a task into HUMAN_REVIEW.

This defeats one of V2's primary governance goals.

**Required transition rules:**

```text
PEER_REVIEW --peer pass--> HUMAN_REVIEW   when human_review_required=true
PEER_REVIEW --peer pass--> DONE           when human_review_required=false
HUMAN_REVIEW --human approve--> DONE
```

The peer-pass transition must require a valid review artifact. Human approval must record approver, timestamp, verdict, and optional notes.

### C-06 — Stale audited tasks remain claimable

The current task is audited against:

```text
b51d4e4
```

The Minchiate spoke advanced through `db7d274` and had reached `1e51ccaf...` during this audit. The requested reviewer implementation already exists. The verification command uses a `--check` option that the script does not implement.

Despite this, the isolated coordinator accepted:

```text
✅ Successfully claimed T-MIN-001 for codex.
stale_claim_exit=0
```

The audit SHA is rendered but never enforced.

**Required fix:** claim must resolve the registered spoke path, inspect its current branch/HEAD/worktree, and compare it with the audit. A differing SHA should force re-audit unless a PM explicitly records that intervening commits are compatible.

Do not merely require the audit SHA to be an ancestor. This task's SHA is an ancestor, yet its scope is obsolete.

### C-07 — Claim remains vulnerable to concurrent success

Task and board destination replacement is atomic, but the operation is not.

The claim sequence remains:

1. load all tasks;
2. inspect locks;
3. mutate memory;
4. replace task file;
5. render/replace board.

Two processes can read the same unlocked snapshot and both report success. The fixed `.tmp` filename also creates contention between writers targeting the same task.

**Required fix for local mode:** acquire an exclusive coordinator lock before reading and hold it through validation, mutation, render, and durable write. Add a task revision and expected-revision check.

**Required fix for distributed mode:** serialize state transitions through a central service/bot or another genuine transactional authority.

### C-08 — Clean clones cannot run the documented CLI

The repository now ignores `.venv`, but `bin/fleet` unconditionally sources it:

```bash
source "$DIR/../.venv/bin/activate"
python "$DIR/fleet.py" "$@"
```

In a clean clone:

```text
.../.venv/bin/activate: No such file or directory
python: command not found
wrapper_exit=127
```

`requirements.txt` exists, but README contains no setup/bootstrap instructions and the wrapper offers no recovery message.

**Required fix:** document installation and make the wrapper locate a usable interpreter or fail with an actionable instruction. A `pyproject.toml` and console entry point would be cleaner.

## High-priority defects

### H-01 — Date-time format checking still silently accepts invalid dates

Although the CLI passes `jsonschema.FormatChecker()`, the environment lacks the optional validator needed to enforce RFC 3339 date-time format.

Scratch result:

```text
created_at: not-a-date
✅ All tasks passed strict schema validation.
lint_exit=0
```

Add the appropriate format dependency and, more importantly, add a self-test asserting a known-invalid timestamp is rejected. A validator whose optional checker silently does nothing launders invalid state with a green message.

### H-02 — Conditional audit fields may all be null

The schema requires audit field presence but defines each field as `string | null`. This passed:

```text
AUDITED accepted with all conditional audit values null
```

Within the AUDITED-and-later conditional, override each property's type to a non-empty string and validate SHA shape.

### H-03 — Handoffs are never schema-validated

`handoff.schema.json` is not loaded anywhere in `bin/fleet.py`. `fleet lint` checks only tasks.

The fabricated one-field handoff demonstrates the consequence.

### H-04 — Evidence is not cryptographic

`fleet verify` prints:

```text
✅ Captured cryptographic evidence ...
```

The artifact is ordinary mutable YAML with no signature, digest, immutable run ID, or binding to repository state.

In a scratch verification run, the generated handoff contained:

```yaml
model: Unknown
branch: test
base_sha: deadbeef
head_sha: REQUIRED_PLEASE_FILL
```

The branch is hard-coded, the model is unknown, the base SHA is copied without validation, and the head SHA is manually filled later.

Rename this to “captured terminal evidence” unless an integrity hash/signature is actually added.

### H-05 — Verification provenance is not captured from Git

`verify` should automatically record:

- actual current branch;
- current HEAD SHA;
- worktree dirty state;
- audit SHA comparison;
- command start/finish times;
- timeout status;
- coordinator version/commit;
- agent and model.

Manual `head_sha` entry is both error-prone and bypassable.

### H-06 — Verification executes unrestricted shell text

`subprocess.run(..., shell=True)` executes the audited YAML field as a shell command with the agent's environment. This may be acceptable for trusted PM-authored commands, but it is an execution authority and must be treated as such.

Risks include shell injection, secret exposure, destructive commands, network access, and unbounded output retained in handoffs.

Prefer structured argv, a controlled working directory, timeout in task schema, output limits, and environment/secret redaction. Document who may audit commands.

### H-07 — The state machine remains incomplete

The schema names states that no command reaches or manages:

- IN_PROGRESS;
- BLOCKED;
- HUMAN_REVIEW;
- DEFERRED;
- CANCELLED.

There is no unclaim, heartbeat, lease expiry, unblock, peer-pass, human-approve, defer, cancel, or archive command.

The commit title “Implement full state machine transitions” therefore overstates the implementation.

### H-08 — Claims have no timestamp or lease

No `claimed_at`, session ID, heartbeat, expiry, or release data exists. Abandoned claims cannot be distinguished from active ones.

### H-09 — Lane eligibility is not enforced

`lane` is stored but claim accepts any owner string. HUMAN and AUDITOR tasks are not mechanically protected.

### H-10 — `audit` does not audit repository reality

`fleet audit` accepts arbitrary `--repo-sha` and `--command` strings. It does not resolve the spoke, verify the SHA exists, ensure the working branch/state, or test the verification command.

“PMs only” is help text, not authorization.

### H-11 — Repository locks release too early

Claim checks only tasks in CLAIMED or IN_PROGRESS. Once a task enters PEER_REVIEW, another task in the same repository can be claimed even though corrections may still be required in the original worktree.

Define whether review states retain repository or path ownership.

### H-12 — Render does not validate before writing

`cmd_render()` uses successfully parsed records without schema or cross-record validation. Invalid records may crash it, while malformed records are silently omitted and render still returns success.

### H-13 — Multi-file transitions are not atomic

Even with `os.replace`, submit writes the handoff directly, then replaces the task, then renders the board. Failure between operations leaves inconsistent state. Handoff writes themselves are not atomic.

### H-14 — The generated board remains a concurrent merge hotspot

Every state transition regenerates `TASKS.md`. Agents changing different YAML files still change the same generated file.

Do not make agents commit the generated board with every claim. Generate it through a serialized coordinator or CI after canonical state is accepted.

### H-15 — No coordinator tests exist

No test files or test configuration were present. The scratch tests above should become regression tests before further phases.

## Documentation drift

README has not caught up with the new CLI:

- it documents only the old claim/manual-update workflow;
- it tells agents to create and edit YAML manually;
- it does not document `audit`, `verify`, `submit`, or `close`;
- it presents a six-state lifecycle while the schema contains eleven states;
- it still calls the system database-backed;
- it still claims massive parallel safety and elimination of Git conflicts;
- it says evidence and peer review are strict even though both are bypassable.

README should describe the current maturity honestly and provide clean-clone setup instructions.

## Recommended next implementation phase

### Phase 4A — Fail closed on invalid state

This is the highest priority.

1. Make parse errors part of lint failure count.
2. Make every mutation call strict full-store validation first.
3. Abort render on any invalid task.
4. Add handoff validation and task/handoff cross-checking.
5. Add regression tests for malformed YAML and fabricated handoffs.
6. Add the missing date-time validation dependency and a self-test.
7. Make audit conditional fields non-null in audited states.

### Phase 4B — Enforce real transition gates

1. Require dependencies DONE before claim.
2. Enforce lane eligibility.
3. Compare audit with live repository state.
4. Add claim timestamp, session/model, lease, and release mechanics.
5. Add peer review artifact schema and `peer-pass`/`peer-fail` commands.
6. Add HUMAN_REVIEW transition and human approval artifact.
7. Make `close` branch based on `human_review_required`.
8. Add block/unblock/defer/cancel/archive commands.

### Phase 4C — Make evidence authoritative

1. Replace shell strings with structured commands or explicitly constrain trusted shell execution.
2. Capture branch, HEAD, dirty state, timestamps, agent, model, and coordinator version automatically.
3. Generate head SHA rather than asking the user to type it.
4. Bind submit to a coordinator-generated verification run ID/hash.
5. Limit/redact captured output.
6. Rename “cryptographic evidence” until cryptographic integrity exists.

### Phase 4D — Add transaction and concurrency controls

1. Add exclusive local coordinator locking.
2. Use unique temp files, flush, `fsync`, and atomic replace.
3. Add task revision/expected-revision checks.
4. Decide and implement the distributed arbitration model.
5. Stop committing generated `TASKS.md` from every concurrent transition.

### Phase 4E — Make installation and documentation reliable

1. Add clean-clone setup/bootstrap.
2. Add `pyproject.toml` or equivalent packaging.
3. Update README from actual CLI behavior.
4. Add `fleet next` with deterministic readiness selection.
5. Add CI running the full adversarial test suite.

## Production-readiness gate

Do not describe V2 as safe for massively parallel autonomous swarms until automated evidence shows:

- invalid or partially readable state halts all mutations;
- exactly one conflicting claim can succeed under concurrency;
- claims cannot bypass dependencies, lane, audit freshness, or repository state;
- submit cannot bypass verification provenance;
- peer and human review gates cannot be skipped;
- clean clones can run the CLI reproducibly;
- generated views do not reintroduce merge conflicts;
- lifecycle transitions and archives are complete;
- every coordinator guarantee has a corresponding negative test proving the forbidden action fails.

## Final assessment

The project is moving in the right direction quickly. Phase 1 corrected important schema weaknesses, Phase 2 introduced safer writes and transition commands, and Phase 3 moved evidence execution into the coordinator. Those are the correct building blocks.

The main remaining issue is semantic enforcement: the coordinator now has the vocabulary of a safe system, but several commands accept artifacts or states without proving how they were produced. The strongest next move is not another feature phase. It is converting this audit's scratch failures into automated negative tests and making them pass one by one.

When malformed YAML blocks the fleet, an OPEN dependency blocks claim, a fake handoff blocks submit, a human-required task blocks close, and a stale audit blocks dispatch, V2 will have crossed the meaningful line from structured task files to enforced coordination.
