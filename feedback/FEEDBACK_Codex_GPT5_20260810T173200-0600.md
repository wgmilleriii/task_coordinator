**Agent:** Codex

**Implementation audited:** `616ee3a96b6ff9abf584f2c54679ecd4e62239b1` (`main`, synchronized with `origin/main` when the final isolated clone was created)  
**Method:** Complete static review plus adversarial execution in isolated local clones  
**Live repository safety:** No engine files, schemas, task records, handoffs, reviews, or logs were changed by this audit. The live checkout contained concurrent untracked log/task work; I preserved it.

## Executive verdict

The coordinator has improved substantially in a few hours. It now has a real Git history and remote, strict top-level schemas, RFC 3339 validation, atomic replacement for task and board files, a local process lock, peer-review artifacts, block/unblock operations, a generated dependency graph, token/cost fields, an archive command, task/global event logging, and explicit agent roles. A real Minchiate task also traversed most of the pipeline. These are meaningful advances.

It is not yet safe to treat as an authoritative autonomous fleet control plane. Its most important safety claims are still stronger than its enforcement:

- the documented `audit` command is a silent no-op that exits 0;
- malformed canonical records are printed and discarded, after which lint and mutations may report success;
- dependency completion is not enforced at claim time;
- handoffs and reviews are schema-checked but not identity-bound to the task or repository;
- a worker can self-review, fabricate evidence, and close a human-gated task as `Unknown`;
- audited and reviewed Git SHAs are not resolved or compared with repository reality;
- archive can invalidate active dependency references;
- the local file lock does not coordinate separate clones or machines;
- the README calls a YAML/Git store “database-backed” and claims conflict-free massive parallelism that the implementation does not provide.

My recommendation is **continue using it as an experimental dispatch board with human supervision, but do not yet make it the fleet's source of truth for authorization, verification, peer approval, or completion**. The next iteration should be a hardening release, not another feature release.

## Critical findings

### C-01 — `fleet audit` silently does nothing

The parser uses `command` for two different meanings:

```python
subparsers = parser.add_subparsers(dest="command", required=True)
audit_parser.add_argument("--command", required=True)
```

For:

```text
fleet audit T-ARC-002 --auditor codex --repo-sha deadbeef --command true
```

the `--command` value overwrites the subparser name. Dispatch therefore sees `args.command == "true"`, matches no branch, falls off the end of `main()`, and exits 0.

Observed:

```text
audit_cli_exit=0
status: OPEN
verification_command: null
```

This is especially dangerous because the exit status falsely tells PM automation that the task was audited.

**Required fix:** give the subparser selector a distinct name such as `action`, and store the verification command under `verification_command`. Add a subprocess-level test asserting output, status transition, persisted fields, board regeneration, and exit status.

### C-02 — The canonical store fails open on malformed YAML

`load_all_tasks()` catches parse errors, prints them, skips the record, and returns only the surviving records. Callers cannot distinguish “all records loaded” from “some records disappeared.”

Observed lint output:

```text
❌ BROKEN.yaml: Failed to parse YAML ...
✅ All active tasks, handoffs, and reviews passed strict schema validation.
lint_exit=0
```

The same corrupt store still allowed claim, render, block, review, and archive operations.

Consequences:

- a malformed claimed task disappears from repository-lock calculations;
- duplicate IDs and dependencies may be evaluated against an incomplete set;
- the generated board silently omits records;
- archive can mutate a partially understood store;
- “strict schema validation” can return green while parsing failed.

**Required fix:** return structured load errors and make every command use one strict preflight that validates all task, handoff, review, and archive records before any read-derived decision or mutation. Invalid canonical state must produce a nonzero exit and zero writes.

### C-03 — Handoff schema validation does not bind evidence to the task

I replaced the generated handoff with a schema-valid artifact containing:

- `task_id: T-FAKE-999` while submitting `T-AUD-003`;
- an unrelated target repository;
- an invented branch;
- non-SHA text for base and head;
- fabricated evidence;
- a different agent/model identity.

`fleet submit T-AUD-003` accepted it and moved `T-AUD-003` to PEER_REVIEW.

The schema verifies shape, not truth. `cmd_submit()` does not cross-check the artifact against the requested task, task owner, registered repository, audited SHA, or live Git state.

**Required fix:** make the coordinator generate immutable evidence fields itself. At submit time, compare task ID, repo, owner, audit SHA, actual branch, actual HEAD, worktree status, verification command hash, command exit status, and a unique verification run ID. Reject manual changes to coordinator-owned fields.

### C-04 — Peer review can be fabricated or self-issued

I supplied a schema-valid review with:

- a different task ID;
- a different reviewed SHA;
- the same worker as reviewer;
- `verdict: PASS`;
- `findings: []`.

`record-review T-AUD-003` accepted it.

There is no cross-binding to the handoff or task, no reviewer independence rule, no proof a review command generated the file, and no minimum review content. A worker can create the artifact directly.

**Required fix:** require and validate:

- exact task ID and handoff run ID;
- exact reviewed HEAD SHA;
- reviewer identity distinct from owner identity;
- an assigned reviewer or signed review request;
- review creation after submission;
- explicit checks performed and evidence references;
- policy for empty findings;
- immutable review timestamps and provenance.

### C-05 — The human gate records neither a human nor approval

After the fabricated peer pass moved a human-required task to HUMAN_REVIEW, I ran `close` without `--human`.

Observed:

```text
✅ Task T-AUD-003 manually closed by Unknown.
close_without_human_exit=0
status: DONE
```

`--human` defaults to `Unknown`, and the name is only printed. No approver, timestamp, verdict, notes, or authentication is persisted.

**Required fix:** make approver identity mandatory, persist a human-review artifact, and require an authenticated or signed approval from an authorized actor. A free-form CLI string is useful metadata, not authorization.

### C-06 — Dependencies are references, not gates

The linter confirms only that a dependency ID exists among parseable active tasks. Claim does not require dependencies to be DONE.

I claimed an AUDITED task whose prerequisite remained OPEN; exit status was 0.

**Required fix:** define dependency satisfaction and enforce it in the atomic claim transition. Usually every dependency must be DONE. Also detect cycles and specify whether CANCELLED or DEFERRED can satisfy a dependency.

### C-07 — Review semantics permit unresolved critical work to become DONE

For a task not requiring human review, I recorded:

```yaml
verdict: PASS_WITH_CORRECTIONS
findings:
  - severity: CRITICAL
    description: Critical correction remains unresolved.
```

The coordinator marked the task DONE.

Every verdict other than literal FAIL is treated as a pass. Finding severity is ignored.

**Required fix:** `PASS_WITH_CORRECTIONS` should enter a correction-required state, or require every correction to carry a resolved status plus evidence and reviewer confirmation. MAJOR or CRITICAL unresolved findings must mechanically block completion.

## High-priority findings

### H-01 — Audit and verification SHAs are decorative

`audit` does not resolve the target repository or validate that `--repo-sha` exists. `claim` does not compare current repository state with the audit SHA. `verify` does not require a Git repository and does not capture HEAD automatically.

In the scratch run, an audited base of `deadbeef` and a non-Git target directory still produced successful verification. The generated branch was `Unknown`, while head SHA remained a manual placeholder.

**Required fix:** create a repository registry and resolve Git state mechanically at audit, claim, verify, submit, and review. Store full 40-character object IDs and reject unknown/dirty/stale states according to explicit policy.

### H-02 — Archive breaks dependency resolution

I created a DONE task `T-ARC-001` and an OPEN task `T-ARC-002` depending on it. `archive` moved the completed task out of `tasks/active/`. The next lint failed:

```text
❌ T-ARC-002.yaml: Dependency 'T-ARC-001' does not exist.
```

The archive also ran while malformed YAML was present.

Additional risks:

- `os.replace(source, dest)` silently overwrites an existing archive file with the same name;
- multi-task archive is not transactional, so a mid-run failure can partially archive;
- archived tasks are not linted as part of canonical history;
- handoffs and reviews are left separate with no archival manifest.

**Required fix:** resolve dependencies across active and archive records, refuse destination collisions, validate the entire store before moving, use a transaction/journal, and archive a task with an immutable manifest referencing its handoff and reviews.

### H-03 — Block/unblock accepts destructive state combinations

`block` accepts every state, including DONE and BLOCKED. Blocking a task twice overwrites the original `previous_status` with BLOCKED. A later `unblock` reports success while restoring BLOCKED and clearing both reason and prior state.

Observed:

```text
✅ Task ... is UNBLOCKED and reverted to BLOCKED.
status: BLOCKED
previous_status: null
blocked_reason: null
```

**Required fix:** reject block on terminal or already-blocked tasks, constrain `previous_status` to an enum, require a non-empty blocked reason while blocked, and encode allowed transitions centrally.

### H-04 — Conditional schema fields may be present but null

AUDITED-and-later tasks require audit keys, but the property types still permit null. A scratch AUDITED task with null audit metadata passed lint. `claimed_at` is not conditionally required, `last_transition` is never maintained, and `previous_status` permits arbitrary strings.

**Required fix:** use state-specific schema branches with non-null, non-empty fields; validate Git SHA formats; require timestamps at the applicable transition; and reject fields that should not exist in earlier states.

### H-05 — Clean clones cannot run the documented wrapper

The wrapper unconditionally sources `.venv/bin/activate`, while `.venv` is correctly ignored. In a clean clone:

```text
.venv/bin/activate: No such file or directory
python: command not found
wrapper_exit=127
```

The README says to run `pip install -r requirements.txt` but does not instruct users to create `.venv`; installing into another environment does not satisfy the wrapper.

**Required fix:** add a bootstrap command or package the CLI with `pyproject.toml` and a console entry point. At minimum, the wrapper should fail once with an actionable setup command.

### H-06 — The lock solves only one narrow race

The global `fcntl.flock` is a real improvement for processes sharing one checkout on Unix. It does not coordinate:

- agents operating in separate clones;
- agents on different machines;
- competing Git pushes;
- manual edits;
- non-Unix systems where `fcntl` is unavailable.

It also serializes read-only lint/render behind long verification commands because the lock wraps the entire dispatch, including the five-minute subprocess.

**Required fix:** use optimistic revisions plus compare-and-swap on a central authority, or a service/database transaction. If retaining local locks, lock only the state transition and use a lease for long-running verification.

### H-07 — Repository lock coverage ends before review is complete

Claim considers only CLAIMED and IN_PROGRESS tasks. Once a task enters PEER_REVIEW or HUMAN_REVIEW, another task for the same repository can be claimed even though corrections may return the first task to IN_PROGRESS.

**Required fix:** retain a lease through review or use scoped locks based on paths/worktrees. Define how correction loops reacquire ownership without colliding with new work.

### H-08 — Render is a mutation over unvalidated input

Render silently skips malformed task records and silently ignores malformed token/cost handoffs. The “all time” burn rate is manually entered, unaudited, and can undercount without warning. Titles are only partially sanitized for Mermaid.

**Required fix:** validate before render, report all ignored artifacts as errors, derive costs from signed usage records where possible, and escape Mermaid/Markdown with a tested encoder.

### H-09 — Evidence is not cryptographic

The CLI calls mutable YAML containing captured stdout “cryptographic evidence.” There is no signature, digest, immutable storage, or chain of custody. `head_sha` is manually typed after the command runs.

**Required fix:** either call it “captured terminal evidence” or add content hashes/signatures and immutable run identity. Never ask an agent to manually fill coordinator-owned provenance.

### H-10 — Verification executes trusted-code-level shell authority

Verification uses `subprocess.run(..., shell=True)` on a YAML string. That permits pipelines and shell syntax but also grants command execution with the worker's credentials and environment.

**Required fix:** define who can author commands, validate structured argv where practical, constrain environment and working directory, cap captured output, redact secrets, and log the exact command digest.

### H-11 — Role separation is prose, not a security boundary

The new Scout/PM/Worker/Reviewer roles are a good operational model, but the CLI accepts arbitrary names and has no credentials or capability checks. A worker can invoke PM, reviewer, and human commands.

**Required fix:** treat roles as policy until there is authenticated identity and authorization. Do not describe them as enforced separation of duties before that exists.

### H-12 — Event logging is useful telemetry, not an audit log

The new per-task `events` array and global `logs/fleet.jsonl` are a useful observability direction, but they do not yet provide authoritative history:

- global log writes and task writes are separate operations with no transaction;
- most transitions log globally before saving the task, so a save failure can leave a phantom event;
- the JSONL file is an append hotspot across clones and is currently untracked in the live checkout;
- embedded task events remain directly mutable with the task YAML;
- several actors are recorded as `Unknown`, and VERIFY uses the model string as actor identity;
- archive has no event;
- tasks already in flight have incomplete histories (the production `T-MIN-001` event list begins at SUBMIT);
- neither log has a hash chain, signature, monotonic sequence, or reconciliation check.

**Required fix:** write transition state and event atomically through one authority. Give every event a unique ID, task revision, authenticated actor, previous/new state, evidence references, and hash/sequence. Add reconciliation that proves the projection matches the event stream.

## Documentation accuracy gaps

The README is clear and approachable, but several statements should be corrected now:

1. **“Database-backed”** — the store is YAML files in Git. That is a valid architecture choice, but it is not a database.
2. **“Massively parallel agent swarms without Git merge conflicts”** — per-task files reduce some conflicts, but every mutation rewrites shared `TASKS.md`; shared handoff/review names and competing pushes remain.
3. **“Strict linear progression”** — the schema exposes additional states, block/unblock creates non-linear paths, FAIL loops to IN_PROGRESS, and archive removes records from active state.
4. **“Cryptographic proof/evidence”** — no cryptographic property exists.
5. **“DONE: work is merged”** — no command checks merge state, target branch, remote containment, or deployment.
6. **“Agents and humans must use the CLI”** — Scouts are simultaneously told to create YAML manually, and current audit cannot function through the CLI.
7. The agent workflow omits `--model`, even though `verify` requires it.
8. The README omits `start-review`, `record-review`, `block`, `unblock`, and `archive` usage.
9. The role list mentions Reviewers in the coordinator instructions but does not define a Reviewer role.
10. Setup instructions do not create the `.venv` required by the wrapper.

## Strengths worth preserving

### 1. Small, inspectable records

One task per YAML file is easy for humans and agents to review. It is a reasonable Git-native prototype format and reduces overlap compared with one monolithic editable board.

### 2. Generated human view

Treating `TASKS.md` as a projection is the right direction. The dependency graph and status presentation improve situational awareness.

### 3. Schema discipline

`additionalProperties: false`, enumerated statuses, minimum lengths, format checking, and separate task/handoff/review schemas are solid foundations. The date-format self-test is especially good defensive thinking.

### 4. Atomic replacement for primary files

Writing task and board temp files followed by `os.replace` prevents basic truncation failures. This should be generalized to all artifacts and wrapped in transaction semantics.

### 5. Explicit lifecycle commands

Named transitions are much easier to test and govern than ad hoc edits. Audit, claim, verify, submit, review, block, close, and archive are the right conceptual vocabulary even though their invariants need strengthening.

### 6. Rapid response to feedback

Several earlier defects were fixed quickly: RFC 3339 support, human-review state routing, handoff/review schemas, local locking, model capture, dynamic branch capture, archive support, event telemetry, and clearer role documentation. The project is learning quickly.

### 7. Repository guardrails

`AGENTS.md` clearly distinguishes engine files from the feedback drop box and requires test-branch work for engine changes. That is useful defense-in-depth for compliant agents.

## Recommended hardening sequence

### Phase 0 — Freeze feature additions and add regression tests

Build a temporary-directory integration suite that invokes the CLI as a subprocess. Every command needs tests for:

- allowed transition;
- forbidden source state;
- malformed YAML/JSON;
- schema violation;
- cross-record mismatch;
- stale/dirty Git state;
- concurrent invocation;
- crash between writes;
- exact nonzero exit semantics.

Include one full lifecycle test from OPEN through archive and at least one correction loop.

### Phase 1 — One strict store loader and transition engine

Create a single function that loads active tasks, archived tasks, handoffs, and reviews; accumulates every parse/schema/invariant error; and returns no usable store if any error exists.

All state changes should call one transition primitive:

```text
transition(task_id, expected_revision, actor, action, evidence)
```

That primitive should enforce source state, destination state, actor capability, dependencies, repository lease, artifact binding, timestamps, and durable audit history.

### Phase 2 — Bind all evidence to Git reality

Register spoke paths/remotes and mechanically capture:

- coordinator commit;
- task revision;
- audit commit;
- spoke remote and branch;
- full base and head SHAs;
- dirty state and diff hash;
- verification command and environment digest;
- start/end timestamps and exit status;
- reviewer identity and reviewed SHA;
- merge commit or remote containment at DONE.

### Phase 3 — Make coordination genuinely distributed

Choose one authority:

- a small transactional service with SQLite/PostgreSQL and authenticated API;
- a GitHub App using checks, reviews, labels, and compare-and-swap updates;
- or a Git-native queue with a bot serializing accepted transitions.

Git files can remain the human-readable projection, but independent workers need an arbiter stronger than a lock file inside one clone.

### Phase 4 — Honest observability and recovery

Turn the current event telemetry into an authoritative append-only transition record with actor identity, failure reason, lease expiry, retry count, command duration, evidence digest, and reconciliation tooling. Provide commands for stale claims, abandoned reviews, conflict repair, and archive restoration.

## Acceptance bar before production authority

I would consider the coordinator ready to become authoritative when all of the following are demonstrated by automated tests:

1. Any malformed canonical artifact makes every mutation fail closed.
2. Audit transitions successfully and validates real repository state.
3. Dependencies and cycles are mechanically enforced.
4. Claim is safe across separate clones, not only processes in one checkout.
5. Verification evidence is immutable and bound to actual Git state.
6. Submit rejects every task/repo/owner/SHA mismatch.
7. Review requires an independent authorized reviewer and exact evidence binding.
8. Unresolved corrections cannot reach DONE.
9. Human-required work cannot close without persisted authorized approval.
10. DONE proves the reviewed commit is merged or otherwise delivered as policy defines.
11. Archive preserves dependency resolution and cannot overwrite history.
12. A clean clone can bootstrap and pass the full lifecycle test from documented commands.

## Final assessment

This is a promising prototype with a good conceptual decomposition and unusually fast feedback uptake. The highest-value design decision now is to stop equating valid YAML shape with trustworthy workflow state. The coordinator needs a fail-closed transition core, artifact-to-task binding, real Git provenance, authenticated separation of duties, and distributed serialization.

Until those exist, the system is useful for visibility and disciplined human-supervised experiments. It should not yet be trusted to prove that work was audited, independently reviewed, human-approved, merged, or safely coordinated across a swarm.
