## System-Level Feedback (task_coordinator engine)

- **`.venv` is not part of the git worktree and worktrees don't inherit it.** A
  fresh `git worktree add` of `task_coordinator` (from `origin/main`, as required
  by the boundary rule) has no `.venv`, so `./bin/fleet` fails immediately with
  `ModuleNotFoundError: No module named 'jsonschema'` and then `python: command not
  found` (the activate script also doesn't exist in the new worktree). I worked
  around this by invoking the primary checkout's existing
  `/Users/willismiller/Documents/GitHub/task_coordinator/.venv/bin/python
  bin/fleet.py ...` directly from inside my review worktree — this reads the venv
  without touching the primary checkout's git state, so it doesn't violate the
  "don't touch the dirty PRIMARY checkout" rule, but it's a workaround, not a fix.
  Suggest either: documenting this workaround explicitly in the README's worktree
  instructions, or having `bin/fleet` fall back to a system Python + `pip install
  -r requirements.txt --user` check when no `.venv` is found next to it, or shipping
  a `bin/fleet-bootstrap` helper that any new worktree can run once. This will bite
  every reviewer/PM/worker who correctly follows the "fresh worktree from
  origin/main" rule.
- **`record-review` does not move the task to `tasks/archive/`.** After
  `record-review T-MIN-023` the task file stays in `tasks/active/T-MIN-023.yaml`
  with `status: DONE` rather than moving to `tasks/archive/`. This matches what I
  observed in the repo's actual behavior, but the README's lifecycle section
  implies archival is part of reaching `DONE`. If this is intentional (e.g. a human
  archives later), consider stating so explicitly in the README lifecycle section;
  otherwise it's a small gap between `close`/`record-review` and the archive step.
- Otherwise the `start-review` → fill YAML → `record-review` flow worked cleanly
  and the schema validation caught nothing wrong once the findings were filled in
  properly (my first pass had verdict defaulted to `FAIL` with a placeholder
  finding, as generated by the template — that's expected scaffolding, not a bug).
