## Root cause: corrected the coordinator's hypothesis

The coordinator's audit hypothesis (PHP `session.gc_maxlifetime` evicting idle session data before the browser's session cookie expires) was already flagged by the coordinator as logically inconsistent with the reported symptom, and I confirmed that by reading the code and reproducing locally: `upvote.php` checks `Auth::user()` (session key `journalgpt_user_id`) *before* `Csrf::validate()` (session key `journalgpt_csrf_token`), and both keys live in the same `$_SESSION` array. If the whole session were GC'd, the 401 auth branch fires first — never the 403 CSRF branch that was actually reported. I verified this directly: emptying `$_SESSION` entirely makes `Auth::user()` return `null` (401), so full eviction cannot produce the reported 403.

**True root cause:** the *only* code path in the entire `journalgpt/` tree that ever changes an *existing* session's CSRF token is `Auth::login()` → `session_regenerate_id(true)` (confirmed via `grep -rn "Csrf::generate\|session_regenerate_id" journalgpt/` — `Csrf::generate()` itself is idempotent and never rotates a token that already exists; only `Auth::login()` triggers regeneration, and it does so unconditionally on every authentication, even a *re*-authentication of an already-logged-in session). Because the `PHPSESSID` cookie (`lifetime => 0`, `path => '/'`) is stored in the browser's shared cookie jar — not scoped per tab — a fresh login in **any** tab/window silently rewrites the cookie that **every other already-open tab** will send on its next request. A long-lived tab that never reloaded still has the old CSRF token cached in `journal-chat.js`'s `csrfTokenInput.value` (read once at page load, confirmed via `grep -n csrfTokenInput`). Its next upvote click authenticates successfully against the *new* session (valid `journalgpt_user_id`, since the login that just happened populated it), but the CSRF check fails because the DOM's cached token is tied to the now-orphaned old session token. This produces exactly "valid auth + 403 CSRF" — no session GC or idle-timing race required at all.

I proved this deterministically (not just narratively) in `journalgpt/tests/CsrfRefreshTest.php::testReproduceAuthPassesCsrfFailsIsA403NotA401`: construct a session with a valid `journalgpt_user_id` but a `journalgpt_csrf_token` that doesn't match the submitted token → `upvote.php` returns HTTP 403 with the CSRF-specific error message, not 401. This satisfies DoD item 1 and resolves the coordinator's stated logical inconsistency.

**For the next agent/PM:** don't assume "user was idle N minutes" is the trigger — it can happen almost immediately if the user (or their password manager) re-submits login credentials while journalgpt is already open in another tab, or after being bounced to `login.php` for any reason (e.g., an actual GC eviction elsewhere) while a second tab stayed open. The GC-eviction angle isn't wrong so much as insufficient on its own — it can be the *first domino* (forces one tab through `login.php`, which then poisons every other tab's cached token), just not the mechanism that directly triggers the 403 itself.

## What I changed
1. `journalgpt/api/csrf_refresh.php` (new) — authenticated endpoint (401 JSON if not logged in, matching `upvote.php`'s existing pattern) that calls `Csrf::generate()` and returns `{"status":"success","csrf_token":"<64-hex>"}`.
2. `journalgpt/assets/journal-chat.js` — upvote click handler now retries exactly once on a CSRF-specific 403 (matched by checking `response.status === 403` and `resData.error` containing "csrf" case-insensitively), fetching a fresh token via the new endpoint, updating the cached `csrfTokenInput.value` in place (so later actions on the same page also benefit), and retrying the identical POST. Only falls back to the existing `alert(resData.error)` if the retry also fails. Refactored the handler into small helpers (`postUpvote`, `isCsrfError`, `refreshCsrfToken`, `applyUpvoteSuccess`) to keep the retry logic readable.
3. `journalgpt/tests/CsrfRefreshTest.php` (new) — follows the existing self-runner convention (no PHPUnit, run via `php journalgpt/tests/CsrfRefreshTest.php`). Covers DoD item 1 (403-not-401 reproduction) and item 2 (a)/(b)/(c). No DB required — both `csrf_refresh.php` and `upvote.php`'s CSRF check `exit()` before ever touching the database, so I didn't need `AskEndpointTest.php`'s DB bootstrap.

**Left untouched (explicitly out of scope per the task):** the chat-send flow (`journal-chat.js:134`, now shifted slightly by my diff) and the share-conversation flow (`journal-chat.js:548`-ish) still read the cached token once with no retry. The task's scope note said not to silently change their behavior without a corresponding DoD item, so I left them as-is. Worth a follow-up task if the same failure mode gets reported against "Ask" or "Share" — the retry-once pattern in this fix would generalize cleanly to both since the underlying cause (shared cookie jar + per-tab-cached DOM token) applies identically.

## Testing note (system-level interest)
`CsrfRefreshTest.php` needed a small amount of test-infrastructure engineering beyond what `AskEndpointTest.php`'s pattern covers: `upvote.php`/`csrf_refresh.php` are procedural scripts that call `exit()` directly after `echo json_encode(...)`, so I couldn't just `include` them in-process like `JournalChatRenderTest.php` does for `index.php` (that only works because `index.php`'s authenticated render path never calls `exit()`). I worked around it by spawning each request as a fresh `php` CLI subprocess (`ini_set('session.save_path', ...)` to a shared temp dir + `session_id()` + `$_COOKIE[session_name()]` to simulate the HTTP cookie), and used `register_shutdown_function()` in the child bootstrap to capture `http_response_code()` even though the target script's own `exit()` runs first (shutdown functions still fire on `exit()`). This is a reusable pattern — if this repo accumulates more `api/*.php` files that need real HTTP-status-level testing (not just unit-level `Auth::`/`Csrf::` calls), it'd be worth promoting this subprocess-runner into a shared test helper rather than having each test file reinvent it.
